
The scenario. A scientist wants to simulate a massive network — millions of neurons — to observe emergent collective behavior, prioritizing simulation speed over bit-perfect hardware accuracy.

What is to be assessed. Two separable things: (1) can any tool here actually reach that scale, and what's the speed/memory trade-off as size grows; (2) is "emergent collective behavior" even the kind of thing anything here is instrumented to observe, independent of whether scale is reachable at all.

Why this is being assessed. The original brief named Brian2CUDA specifically as an example framework, and this project's comparison table doesn't include it — that's a named deviation from the brief, not a silent omission, and it needs an honest reason, not just an acknowledgment.

What can be assessed, with what already exists:

The scaling instrument itself, already built: snnbench/microbench.py's sweep_axis("width", ...)/sweep_axis("depth", ...) and its T×batch grid already characterize exactly the trade-off Story D asks about — speed and memory as network size grows — with OOM captured as first-class data, not a crash. It hasn't been run at millions-of-neurons scale, but the instrument for characterizing that trade-off as size increases already exists and works.
The reason scale is actually blocked, already diagnosed, not assumed: every framework in this lineup trains via BPTT, which requires holding every timestep's activations in memory simultaneously for the backward pass — memory scales with T × batch × neurons. This is a real, already-measured structural ceiling (the same mechanism behind the N-Caltech101 OOM finding), not a vague "it might be slow." At millions of neurons, this makes the current approach intractable regardless of GPU size — a real reason, not an excuse.
The actual path, already named and scoped: Tier B — OTTT, e-prop, FPTT — credit-assignment alternatives to BPTT with constant memory regardless of timestep count, already cited with real sources, already explicitly scoped as a stretch goal rather than this semester's committed work.
A fifth connection for Brian2CUDA, not previously named: Brian2/Brian2CUDA's own heritage is large-scale computational-neuroscience simulation, and it doesn't use BPTT at all — local plasticity or fixed dynamics only — which sidesteps the exact memory ceiling blocking everything else here. That makes it relevant to Story D specifically, on top of B, C, F, and H already established — five stories, not four, touched by the same one unbuilt integration.
What cannot be assessed, and a second gap worth naming on its own: actual millions-of-neuron execution — blocked structurally, not just untried. And separately, even if scale were solved, nothing in this portfolio observes emergent collective behavior — population-level oscillation, synchrony, avalanche statistics — since every instrument here (accuracy, energy, latency, spike rate) measures task performance, not collective dynamics. That's a second, independent gap that scale alone wouldn't close.

The end conclusion: Story D is not answered, but the "not answered" is precise: blocked by a real, already-diagnosed structural limit (BPTT's memory scaling), with the actual fix already named twice over (Tier B, or Brian2CUDA — now confirmed relevant to five stories, the widest reach of anything in this portfolio) — and a second, separate, currently-unaddressed gap in emergent-behavior instrumentation that neither fix alone resolves.
