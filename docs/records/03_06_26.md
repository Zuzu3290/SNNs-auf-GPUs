|------|-----------------|
| Custom CUDA kernel (`snn_forward`) | **1.455 ms** |
| PyTorch baseline (Python LIF loop over T timesteps) | 4.727 ms |
| **Speedup** | **3.25×** |

The PyTorch baseline iterates over T=25 timesteps in Python, calling
`v_new = v * (1 - tau_inv) + x` and `(v_new >= v_th).float()` per step.
The custom kernel fuses all timesteps into one GPU launch, eliminating the
Python loop overhead and reducing kernel launch count from 25 to 1.

## Benchmark — Temporal Kernel (`temporal_forward`) vs PyTorch Baseline

100 forward passes averaged. Input `[4, 512, 25]`.

| Path | Time per forward |
|------|-----------------|
| Temporal CUDA kernel (`lif_temporal_cuda`) | 1.541 ms |
| PyTorch baseline (Python LIF loop over T) | 2.278 ms |
| **Speedup** | **1.48×** |

### Why lower than the basic kernel's 3.25×

The temporal kernel launches **B×N = 2 048 threads** (one per neuron).  
The basic kernel launched **B×N×T = 51 200 threads** (one per timestep).

A T4 has 2 560 CUDA cores across 40 SMs. At 2 048 threads the GPU is running
at roughly 4% occupancy — most SMs are idle. The voltage-in-register approach
eliminates the race condition and T global-memory round-trips, but at this
input size the parallelism reduction costs more than the memory savings gain.

The speedup curve for the temporal kernel is input-size dependent:

| B × N (threads launched) | Expected behaviour |
|--------------------------|-------------------|
| 2 048 (current) | Under-saturated — 1–2× |
| 16 384 | Approaching saturation — 3–5× |
| 65 536+ | Fully saturated — maximum gain from register reuse |

**Conclusion:** the temporal kernel is the correct kernel for production
(no race condition, accurate LIF dynamics). The 3.25× figure from the basic
kernel was a benchmark artefact — faster due to higher raw parallelism at the
cost of incorrect temporal ordering. At production batch sizes
(B ≥ 32, N ≥ 4 096) the temporal kernel will pull ahead.

## Notes

- Basic kernel benchmark (3.25×) is a performance artefact; the kernel has a
  race condition and does not compute correct LIF dynamics at B×N×T parallelism.
- Temporal kernel benchmark (1.48×) is the correct baseline at `[4, 512, 25]`;
  speedup scales with B×N — test at larger inputs for the real ceiling.
- NVML energy readings require a bare-metal GPU; remove `-DSNN_HAS_NVML=0`
  from `setup.py` on local hardware to enable real power and energy measurements.


The current kernel has a fundamental issue that also limits performance: it launches one thread per (b, n, t) — but LIF has a temporal dependency where v(t) depends on v(t-1). With T threads all reading and writing voltage[b*N + n] simultaneously, the temporal sequence is a race condition. The speedup measured is real (fused launch vs Python loop) but the kernel is not computing the correct LIF dynamics under concurrent writes.

The researched approach that fixes this and gives the real performance edge is temporal register tiling — the same pattern used in efficient RNN/LSTM CUDA kernels:

Launch B×N threads (one per neuron, not per timestep)
Each thread owns one (b, n) neuron and loops over T in order
Voltage lives in a register for the entire T loop — zero global memory traffic for the state
Spikes written out per step, inputs streamed in sequentially
On top of that, warp ballot (__ballot_sync) gives a free warp-wide spike mask per step — enabling sparse downstream propagation (only send spikes where neurons actually fired).

The two together match what SpikingJelly's cupy backend and Norse's CUDA kernels do internally.

Concretely:


Current:   B×N×T threads, voltage in global mem, race condition
Fixed:     B×N   threads, voltage in register, T loop in-thread
Addition:  __ballot_sync → spike mask per warp per timestep
Expected gain over the current 3.25× result: significantly higher correctness + another 2-4× throughput from eliminating the T global memory round-trips.


lif_temporal.cu — the corrected kernel. Template <bool WriteMask> gives two instantiations with zero runtime branch cost. Key mechanics:

__ballot_sync(0xffffffff, active) first — all warp threads agree on who is in-bounds before diverging
Voltage v lives in a register for the full T loop — no global memory traffic for state
__ballot_sync(active_mask, fired) each step — 32-neuron spike bitmap, lane 0 writes it to spike_mask[warp, t]

The core issue is clear: the temporal kernel dropped from 51,200 threads to 2,048 — most SMs are idle. The "oriented machines" principle is SM-saturation regardless of input size: launch exactly enough blocks to fill every SM via a grid-stride loop, so each thread handles multiple neurons when B×N is small. And the energy profiler should feed back into the next launch's config dynamically — not just report, but adapt.


SM saturation — lif_warp_oriented_kernel launches sm_count × target_blocks_per_sm blocks. On a T4 (40 SMs, target=8) that's 320 blocks × 256 threads = 81,920 threads active, regardless of whether B×N is 2,048 or 2,000,000. The grid-stride loop handles the distribution — at small B×N each thread still processes exactly one neuron; at large B×N threads loop over multiple. Every SM stays busy either way.

Adaptive energy feedback — dispatch_warp_oriented in engine.cu keeps two static variables (s_last_elapsed_ms, s_blocks_per_sm) that survive across calls. After each launch it decides:

< 0.5 ms → GPU was idle, push harder (blocks_per_sm++)
> 2.0 ms → GPU is under pressure, back off (blocks_per_sm--)
Dead-band [0.5, 2.0 ms] → leave unchanged
This is the energy-management runtime adaptation you described — the profiler now informs the next launch, not just reports.

Dispatcher routing — KERNEL_CONFIG_ACCELERATED now points to warp_oriented by default. The full priority order in snn_engine_dispatch is:


accelerate: false         → lif_basic (256 threads, benchmark ref)
accelerate + warp_oriented → dispatch_warp_oriented (SM-saturating + feedback)
