Sinabs/Speck isn't hypothetical here — it's already sitting in the framework lineup. Same full structure.

The scenario. A developer with an already GPU-trained model wants to deploy it onto a specific, low-power neuromorphic chip for an IoT device. They need the weights and the event-driven dynamics to translate correctly from the GPU training environment to that target hardware, and need to know which tool actually minimizes the performance gap between the two.

What is to be assessed. Three separate things, not one: (1) do the trained parameters — weights, threshold, decay/tau — actually export into a format the target hardware's own toolchain can consume; (2) do the event-driven dynamics the model was trained under match what real spike-driven hardware would actually produce, the same discretization question as Story B's timing half; (3) how much of the overall "performance gap" is attributable to fixable software/format issues versus hardware-specific effects that no amount of software work closes.

Why this is being assessed. Because "train on GPU, deploy to a neuromorphic chip" is the premise this whole story rests on, and nothing guarantees that premise holds by default — the actual export mechanism and the actual dynamics both need checking against real models, not assumed to work because the frameworks are theoretically compatible.

What can be assessed, with what already exists:

Parameter translation, tested against real trained models, not assumed: NIR export was run against this project's actual models. Norse exports cleanly — real Conv2d/CubaLIF/Affine nodes with real trained weights, tau, threshold. The other three have specific, diagnosed, scoped bugs: snnTorch's bundled NIR code calls a nir.LIF(v_reset=...) parameter the installed nir package no longer has; SpikingJelly's documented nir_exchange module isn't present in the installed build; Sinabs' exporter explicitly rejects MaxPool2d. Each has a named fix, not an open-ended unknown.
A real vendor deployment path, not a hypothetical one: Sinabs is SynSense's own training library, built specifically for their Speck/DYNAP-CNN chips — a real, low-power, always-on edge/IoT vision chip, which is almost exactly Story C's own persona. This is the one framework in the lineup with an actual route to specific silicon.
The algorithmic component of the gap, quantified twice already: dt_aware_lif's measured discretization-fidelity result (timing), and the SynOps-vs-real-GPU-power gap already computed by SNNTrainer/SNNTester (Horowitz 45nm energy proxy against real NVML-measured power) — both already separate "this part of the gap is ours to fix in software" from "this part needs real hardware," the same distinction Story B needed.
Whether specialized hardware is even justified for this workload: the sparsity-vs-GPU-crossover argument — real per-layer firing rate from ActivityMonitor's hidden-layer buffers, compared against a literature-cited threshold for where sparse execution actually pays off — answers why Story C's persona would want dedicated hardware at all, not just how to get there.
What cannot be assessed, and one sharp point worth naming precisely: Sinabs' own NIR exporter rejects MaxPool2d — and this isn't only an export-format inconvenience. If Sinabs' exporter treats MaxPool2d as unsupported, that's a real signal about what SynSense's own Speck toolchain likely accepts, meaning the architecture itself — not just the export call — may need to change (e.g. AvgPool2d or a strided convolution in place of MaxPool2d) before real Speck deployment is even architecturally possible, separate from whether the export bug gets patched. Beyond that: no full graph round-trip has been tested on Speck's own runtime, and no real deployed latency or power number exists on actual silicon — the same hardware-access dependency Story B's power half has.

The end conclusion: Story C is the most substantively answered of the hardware-adjacent stories. Real vendor infrastructure exists, not hypothetical; three of four frameworks have specific, scoped export fixes rather than unknowns; the algorithmic half of the gap is already quantified twice over. What's left is concrete and named: close the three NIR bugs, resolve whether the network's own pooling strategy needs to change for real Speck compatibility, and then the same hardware-access dependency as Story B — real deployment and real measurement on physical silicon — for the final numbers.
